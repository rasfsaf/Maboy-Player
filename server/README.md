# Maboy API — первый этап

Серверная основа по `../target.md`: учетные записи, изоляция данных по пользователям,
идемпотентные операции и инкрементальная синхронизация библиотеки, плейлистов и очереди.
Это **не** готовый плеер: Flutter-клиент, загрузка медиа, OAuth, offline-хранилище
и конфликты при одновременном редактировании с разных устройств — следующие этапы.

## Локально

Из каталога `server`:

```powershell
uv run --extra test pytest -q
uv run uvicorn maboy.app:app --reload
```

По умолчанию используется SQLite-файл `maboy.db`. API-документация: `/docs`.
Для PostgreSQL задайте `DATABASE_URL=postgresql+psycopg://...`.

## Docker Compose (VPS)

Создайте `server/.env` с `POSTGRES_PASSWORD=` (случайный сильный пароль),
затем в каталоге `server` выполните `docker compose up -d --build`.
Порт API слушает только `127.0.0.1:18181`: перед публикацией подключите HTTPS
через reverse proxy. Не запускайте публичный HTTP с bearer-токенами.
Развёрнуто отдельно на `happ-germany` в `/opt/maboy/server` (`maboy-db-1`,
`maboy-api-1`). Внешний HTTPS-маршрут ещё не настроен; существующие сервисы
и прокси-конфигурации не менялись. Локальный healthcheck:
`curl http://127.0.0.1:18181/health`.

## Протокол

`POST /auth/register`, `POST /auth/login` возвращают bearer token.
`POST /sync/operations` принимает `operation_id` (UUID), `kind` и `payload`.
`GET /sync/operations?after=0&limit=100` возвращает операции и курсор.
Поддерживаемые виды операций: `track.upsert`, `playlist.upsert`,
`playlist.delete`, `playlist.set_tracks`, `queue.set`, `favorites.set`,
`history.add`, `track.device_status`, `equalizer.preset.upsert` и
`equalizer.preset.delete`. Операции со списками заменяют полный
упорядоченный список. Повтор с тем же `operation_id` возвращает прежнюю версию,
а повтор с иным содержимым отвергается. При реконструкции клиент применяет
операции по `version` и хранит собственный курсор локально.

В текущем прототипе нет snapshot/compaction, удаления треков и плейлистов,
refresh/revoke токенов, миграций схемы, rate limiting и разрешения конкурентных
правок: до запуска с реальными пользователями они обязательны.

## Синхронизация пресетов эквалайзера

### Было

Сервер не знал о звуковых профилях. Клиент не мог переносить собственную кривую
между Windows и Android.

### Стало

`equalizer.preset.upsert` принимает только логическую модель пресета:

```json
{
  "id": "UUID",
  "name": "Metal room",
  "gains": [5.5, 2.5, -0.5, 0.0, 2.0, 3.5]
}
```

Имя после trim должно содержать 1–40 символов. `gains` — ровно шесть конечных
чисел в диапазоне `-12..+12`. `equalizer.preset.delete` принимает только
`{"id":"UUID"}`. Payload канонизируется до проверки идемпотентности, поэтому
повтор исходной операции с тем же ID стабильно возвращает `duplicate=true`.

Любые лишние поля, включая `active`, `enabled` и ручное состояние, удаляются до
записи в журнал. Это жёсткий серверный инвариант: между устройствами передаётся
определение пользовательского пресета, но не локальный выбор устройства.
Изменений схемы БД нет — пресеты реконструируются из существующего журнала
операций, как другие offline-first сущности.

### Влияние и миграция

Старые клиенты игнорируют неизвестные операции, новые клиенты восстанавливают
пресеты при обычном incremental sync. Миграция БД не требуется. Серверный
регрессионный тест:

```powershell
uv run --extra test pytest -q tests/test_api.py -k equalizer
```

## Исправление передачи файлов и уникальности локальных треков (Relay & Local Tracks)

### Было

1. **Коллизия `source_id` для локальных треков**:
   - При импорте локальных файлов старый клиент передавал `source_id: deviceId`. Серверная логика `apply_mutation` искала существующий трек с тем же `(user_id, provider, source_id)` и вместо добавления новых записей перезаписывала название одного и того же первого трека. В результате сотни треков не попадали в таблицу `tracks`.
   - При попытке реле-передачи (`/relay/{id}/source` или `/relay/{id}/receive`) метод `relay_identity` проверял наличие трека в БД: `track = db.get(Track, id)`. Поскольку трек отсутствовал в таблице, соединение отвергалось с ошибкой 403 Forbidden (`code=1008`).
2. **Пассивное ожидание и долгие таймауты**:
   - `relay_receive` ожидал доступности источника до 30 секунд без оповещения устройств в сети. Если отправитель не открыл сокет заранее, передача завершалась таймаутом `retry`.

### Стало

1. **Гарантированная уникальность и изоляция локальных треков**:
   - Для `provider == "local"` сервер не производит слияние треков по `source_id`: каждый трек уникален по своему `id`. Если `source_id` не оканчивается на `item.id`, он автоматически нормализуется в формат `f"{item.source_id}:{item.id}"`, предотвращая любые коллизии в рамках `UniqueConstraint("user_id", "provider", "source_id")`.
   - В существующей базе данных на VPS выполнена миграция-бэкфилл из журнала `operations`: все 527 треков восстановлены в таблице `tracks`.
2. **Сигнализация реле по требованию (`relay_request`)**:
   - При подключении получателя в `relay_receive`, если отправитель ещё не открыл сокет раздачи для этого трека, сервер мгновенно отправляет подключённым клиентам пользователя в сокет `/sync/events` сообщение:
     ```json
     {"type": "relay_request", "track_id": "<track_id>"}
     ```
   - Устройство-источник, получив сигнал, автоматически подключается к раздаче по требованию.
   - Таймаут ожидания источника снижен с 30 до 10 секунд.
